# WARREN

Coordinated abuse-ring detection for card-not-present payments.

A rabbit warren looks like separate burrows from the surface. WARREN finds the
tunnels: sets of accounts that transact as if unrelated but are worked by one
coordinated operation — the loss class per-transaction scoring structurally
cannot see, because every individual transaction in a ring can look ordinary.

The unit of defence is the ring, not the payment.

## Status

Under construction. Ingest and entity resolution are in place for both datasets;
detection and evaluation are not yet built.

## Data

**[IBM Anti-Money Laundering](https://www.kaggle.com/datasets/ealtman2019/ibm-transactions-for-anti-money-laundering-aml)**
(HI-Small) is the primary dataset: 5,078,345 transfers between 518,581 accounts
owned by 166,207 entities, of which 0.1019% are laundering. It ships an explicit
sender-to-receiver graph and, unusually, **370 labelled rings across 8 named
typologies** — CYCLE, FAN-IN, FAN-OUT, GATHER-SCATTER, SCATTER-GATHER, STACK,
BIPARTITE and RANDOM. It is synthetic, generated by a multi-agent simulator.

**[IEEE-CIS Fraud Detection](https://www.kaggle.com/c/ieee-fraud-detection)**
is real card-not-present data: 590,540 transactions at a 3.499% fraud rate. It
carries no ring labels, only a per-transaction flag.

Ring detection was attempted on IEEE-CIS first and **failed** — 1.05x
enrichment, no signal — because the fields that would tie separate accounts to
one operator are not in the data. That result, and the two artefacts that
initially disguised it, are written up in [docs/FINDINGS.md](docs/FINDINGS.md).
IEEE-CIS is kept for its account-level signal, where fraud concentrates 36x
above chance.

## Running it

Requires Go 1.24+, Docker, and a Kaggle account that has accepted the
competition rules.

```sh
docker compose up -d                       # Postgres on :5432

python3 -m venv .venv && .venv/bin/pip install kaggle
.venv/bin/kaggle competitions download -c ieee-fraud-detection -p data/
unzip data/ieee-fraud-detection.zip -d data/

go run ./cmd/ingest -data data             # ~65s, streams via COPY
go run ./cmd/rings                         # entity resolution over IEEE-CIS
```

For the AML dataset:

```sh
for f in HI-Small_Trans.csv HI-Small_Patterns.txt HI-Small_accounts.csv; do
  .venv/bin/kaggle datasets download ealtman2019/ibm-transactions-for-anti-money-laundering-aml \
    -f "$f" -p data/aml/
done

go run ./cmd/aml-ingest -data data/aml -set HI-Small   # ~55s
```

Every loader applies its schema from scratch, so all are safe to re-run, and
each finishes by printing the figures that prove the load is faithful:

```
transactions=590540 frauds=20663 rate=3.4990% identities=144233 amt=[0.251..31937.391]
transactions=5078345 laundering=5177 (0.1019%) in_labelled_ring=3209 accounts=518581 entities=166207
pattern transactions matched to ledger: 3209/3209 (100.00%)
```

Those match the published datasets exactly. If they drift, rows were dropped or
mangled on the way in. The 100% pattern match rate matters most: it is the check
that the ring ground truth actually attached to the ledger rather than silently
landing on nothing.

## Layout

```
cmd/ingest/        IEEE-CIS  -> Postgres via the COPY protocol
cmd/aml-ingest/    IBM AML   -> Postgres, including the ring labels
cmd/rings/         entity resolution and ring linking, with a concentration report
internal/aml/      AML schema, loader and patterns-file parser
internal/csvutil/  field parsing shared by both loaders
internal/db/       connection handling and IEEE-CIS schema
internal/graph/    union-find, entity resolution, link rules
docs/FINDINGS.md   measured results, including the rejected hypothesis
data/              raw CSVs (gitignored)
```

`DATABASE_URL` overrides the local development database.
